01 / 容量估算

把“很多人使用”变成量级

修改四个演示假设，观察每天请求、峰值请求和同时运行的模型调用。

每日对话请求—DAU × 轮次
峰值请求 / 秒—日均请求 / 秒 × 峰值倍数
约同时进行的模型调用—峰值请求 / 秒 × 响应秒数

这是粗略估算：先用日均请求率乘峰值倍数，再按平均响应时间估计同时运行的调用。实际并发、Token 用量、费用和供应商限额必须通过日志与压测确认。

02 / 高层设计

一轮对话怎样走完

先保障用户看得到回复，再处理可后移的动作事件。

  1. 输入
    小云桌面端

    发送带会话 ID 的消息；重复提交有同一请求 ID。

  2. 入口
    身份、配额与限流

    控制单用户和整体调用量，防止模型额度被突发流量耗尽。

  3. 主链路
    对话服务 → 模型

    读取必要上下文，调用模型并把回复流式送回客户端，同时保存消息。

  4. 后续事件
    动作选择 → 动作库

    把可后移的动作任务交给事件处理，挑选匹配片段并通知桌面端播放。

  5. 观测
    延迟、错误、积压与成本

    监控实际峰值和失败路径，再决定是否扩容或拆分服务。

PRODUCT DIRECTIONS / 可扩展方向

从知识主题延伸产品方向

下面是结合你现有 AI、动作与三维交互研究提出的候选方向。先确认用户目标，再选择相关章节；它们不是上游仓库已实现的产品。

01 / 现有方向

AI 互动角色

让“小云”完成对话、记住必要状态，并在合适时机触发动作。先做单人闭环；多人使用时再评估容量、限流与观测。

参考：03、12；多人阶段 02、04、19、20
02 / 素材能力

动作与媒体素材库

把采集或生成的动作片段组织成可搜索、可上传、可同步的素材，并按需分发给桌面角色。

参考：13–15、24；通知需求出现时看 10
03 / 空间能力

附近与空间体验

如果三维交互产品需要附近地点、好友位置或地图导航，再借鉴位置索引与地图服务的设计问题。

参考：16–18
04 / 条件方向

预约与交易

只有出现付费、库存或预约需求时，才深入研究防超卖、支付重试、账目核对和撮合规则。

参考：22、26–28

任何方向上线后都需要实测延迟、错误和成本，并单独确定隐私、安全与数据治理要求；第 20 章可作为监控设计的参考。

WHY IT MATTERS / 对我的意义

让已有产品研究
补上服务端视角

本总仓库已有 AI 工程、三维交互和网页产品研究。这份笔记能帮助你进一步问：如果一个原型从少数体验者走向大量用户，服务端怎样承载请求、存储数据、应对故障，并控制成本？

它提供思考与沟通的框架。真正落地时，还需要把章节中的假设换成你的指标，做原型、压测和故障验证。

先学第 2、3 章估算与设计框架
再选一个贴近业务的案例聊天、存储、通知或支付
最后做自己的方案与验证指标、架构图、风险和实验
